1. OVERVIEW
================================================================================

This project implements a "manual/admin-verification" payment model — no real
payment gateway (Stripe, PayPal, etc.) is fully integrated. The system
supports 7 payment method types, but only two are actively implemented:
manual_bank_transfer (fully) and card (sample/demo placeholder).

PayHere credentials exist in .env.example but are NOT wired up. The card flow
is explicitly designed as a pre-PayHere simulation.

3. GUEST vs REGISTERED USER FLOW
================================================================================

3A. Guest Tracking
    File: Server-side/Middlewares/guest-tracking-middleware.js
    - A guestToken cookie is set for unauthenticated visitors
    - Guests place orders by providing an email address

3B. Guest Order Creation
    File: Server-side/Controllers/order-controller.js:145-159, 295
    - If req.userInfo is null but guestEmail exists, a Guest record is
      created/updated via findOneAndUpdate with upsert:true
    - The order references guest._id instead of user._id

3C. Guest OTP Verification for Bank Transfers
    File: Client-Side/src/pages/shopping-view/Checkout.jsx:739-747
    - Guests must pass OTP verification before submitting a bank transfer order

3D. Guest Payment Authorization
    File: Server-side/Controllers/manualPaymentController.js:73-111
    - authorizePaymentAccess middleware allows guests to access their payment
      by matching the email used at checkout
    - Supports email-based auth via x-payment-email header or body field

3E. Guest Payment Recovery
    File: Client-Side/src/pages/FindPaymentPage.jsx
    - Guests can look up payments using email + reference number
    - API: POST /api/v1/manual-payments/lookup (manualPaymentController.js:1494-1545)

3F. Registered User Flow
    - Orders reference authenticated User._id (order-controller.js:294)
    - Users can access GET /api/v1/orders/user-orders (requires auth)
    - Users can generate references via POST /api/v1/manual-payment/generate
    - Users see pending payments via GET /api/v1/payments/my-pending

8. KEY ARCHITECTURE DECISIONS
================================================================================

  1. No real payment gateway is fully integrated. The system uses a
     manual/admin-verification model. PayHere credentials exist in config but
     are not wired up yet.

  2. Shared collection model: Both manual_bank_transfer and card payment types
     share the ManualPayment collection, differentiated by the paymentType
     field. This is by design.

  3. Two-tier verification for bank transfers:
     - OCR layer (Tesseract.js): Sanity-check on the uploaded receipt image
     - Bank confirmation layer (IMAP/SMS): Actual proof of funds via bank
       email notification polling or SMS webhook

  4. Idempotent processing: bankVerification.emailMessageId has a partial
     unique index to prevent double-processing of the same bank notification.

  5. Never store full card details: Only last4, brand, cardholder name, and
     expiry are stored. Full PAN and CVV are NEVER persisted.

  6. Guest support: Complete guest checkout flow with email-based
     authentication for payment access and recovery.

  7. 24-hour payment expiry with one-time 12-hour extension option.

  8. Multi-channel notifications: Every payment state change triggers email,
     WhatsApp, in-app notification, and Socket.IO real-time events.

  9. Transaction safety: Order creation is wrapped in a MongoDB transaction
     when topology supports it (falls back gracefully on standalone MongoDB).

 10. Cart is stored client-side in localStorage (not server-side), cleared on
     successful order creation.
